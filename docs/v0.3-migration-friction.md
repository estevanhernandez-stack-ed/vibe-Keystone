## Gate 2 — `Project-626Labs-1/CLAUDE.md` (302 lines) — BLOCKED, and it found the cycle's worst defect

**Skeleton performance: a real defect, fixed at the gate.** The migration did not proceed. Reading the file surfaced a failure mode neither v0.2.1 nor the v0.3 spec accounted for.

### F-05 — Keystone would overwrite generated files — SHIPPED-DEFECT CLASS, fixed in `f985e5c`

**Severity: critical. This would have shipped.**

`Project-626Labs-1/CLAUDE.md` is not hand-authored. It has two owners:

| Lines | Owner | Regenerated by |
|---|---|---|
| 1-201 | `CLAUDE.template.md` (191 lines, `{{agents.lead.name}}` interpolation) | `npm run vars:resolve` → `scripts/vars-resolver.ts` (34KB) + `agent-vars.json` + a JSON schema |
| 202-302 | GitNexus tooling, `<!-- gitnexus:start -->` / `<!-- gitnexus:end -->`, absent from the template | `npx gitnexus analyze`, plus a PostToolUse hook after every commit |

Nothing in Keystone asks whether the file it is about to regenerate is itself generated. Run `/keystone` here and it produces a well-formed CLAUDE.md that is **silently erased on the next `npm run vars:resolve`**, with the GitNexus block re-injected after the next commit. No error, no warning, no signal that the work evaporated.

The v0.2.1 skill's only guard is "read it before overwriting; show a diff." A diff against a generated file looks completely normal.

**Fix applied at the gate rather than deferred:** `skeleton.md` gains a "Before you write: find out what owns the file" section — detect generated-file headers, sibling templates, interpolation syntax, render scripts in `package.json`/Makefile, and tool-owned marker regions; retarget the template; leave tool-owned regions alone; tell the builder before writing. A file can have more than one owner, so the ownership map is established before the first edit.

**Why this is the cycle's most valuable find:** it is invisible to every check that existed. It is not a style question or a judgment call. It is a class of repo where the tool's core operation silently does nothing, and only a real-file dogfood on a repo with real tooling could surface it. Gate 1 on a hand-authored file could never have found it.

**Provenance note:** the checklist anticipated this class of trap — item 9 tells the migration to check `vibe-cartographer` for a generator before cutting, because the harness comparison had flagged it as "half auto-generated." The trap was real; it was just in a different repo, three items earlier than expected.

### F-09 — Keystone found a trap that was not in the file — PROVES THE `/doctor` BOUNDARY

The spec's key technical decision #1 claims Keystone and `/doctor` differ by **input**: Keystone reads the repo and can therefore surface a gotcha nobody wrote down; `/doctor` reads the file and can only remove or relocate what is already there. That was an argument. Gate 2 turned it into evidence.

Classifying the template surfaced that **two different VS Code extensions exist in the repo**:

| Path | Package | Version | Tracked files | Last commit |
|---|---|---|---|---|
| `/vscode-extension/` | `626labs-vscode` | 0.1.0 | 48 | 2026-07-06 |
| `/tools/vscode-extension/` | `project-626-vscode` | 0.0.1 | 12 | 2026-05-24 |

Different package names, so not a duplicate clone — two separate extensions, one active and one apparently superseded. An agent told to "work on the VS Code extension" has a coin flip, and the losing side is a stale tree nobody has touched in two months.

**This gotcha appears nowhere in the old CLAUDE.md.** It could not: it is a fact about the repo, not about the file. `/doctor` scanning the existing keystone would never produce it. The regenerate-versus-trim distinction is real, and this is the proof.

Corollary worth carrying: a migration is not only subtractive. Reading the repo to classify existing lines surfaces content that should have been there all along.

### F-12 — Marker-region extraction must anchor to line starts — AGENT ERROR, caught before commit

Splicing `vibe-cartographer/CLAUDE.md` clobbered its 101-line GitNexus block on the first attempt. Cause: the extraction used a plain substring search for `<!-- gitnexus:start -->`, and that string appears **three times** in the file — twice inside prose (lines 90 and 100, where the keystone documents the block's ownership) and once as the actual block delimiter at line 104. The first match won, so the splice captured a fragment of a sentence instead of the block, and the file went 204 to 52 lines.

Caught by the post-write verification, restored with `git checkout` before any commit. Redone with extraction anchored to `line.strip() == marker` plus a length assertion, which produced the correct 204 to 152.

**The irony is the finding.** `skeleton.md` tells the agent to leave tool-owned marker regions alone. It does not say *how to identify the region*, and the naive approach fails precisely on the files that are careful enough to document their own markers. A repo that writes down "don't hand-edit between these markers" is a repo where those markers appear in prose.

**Carry to item 10:** `skeleton.md`'s ownership section should say that marker regions are identified by lines that consist solely of the marker, never by substring search, and that the extracted region's size should be asserted before it is used.

Also worth noting for `/reflect`: the verification step is what caught this. A migration that trusted its own splice would have committed a 52-line file with 101 lines of tooling silently deleted, and the next `npx gitnexus analyze` would have re-injected it, making the loss look like churn rather than damage.

`Projects/CLAUDE.md` cut 42 percent where `vibe-plugins` cut 69. That is the right outcome and worth recording, because a migration that always produces a dramatic reduction would be evidence the gate is cutting on length rather than derivability.

### F-14 — Epic 5's untestable criterion stayed untested — HONEST GAP

`prd.md > Epic 5` claims "an agent reading only `SKILL.md` behaves correctly", and `spec.md > Open Issues` item 3 named the honest verification: watch whether the migrations force repeatedly opening references that `SKILL.md` should have summarized.

Across all five migrations, the reference files were not re-opened. That looks like a pass and is not one. **The agent running these migrations is the agent that wrote the references this session** — the content is in working context, so "did I need to open the file" measures nothing.

The criterion needs a cold agent: a fresh session, given only `SKILL.md`, asked to migrate a real keystone, with the count of reference-file opens recorded. Until that runs, Epic 5's last criterion is unverified rather than met. Recording it as unverified in `/reflect` rather than claiming the pass.
