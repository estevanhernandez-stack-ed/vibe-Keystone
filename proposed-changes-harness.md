## Summary

Keystone is the strongest tool we have on the source-of-truth axis — it *produces* the load-bearing context file, which is exactly what OpenAI calls the harness's ground floor. But it ships at the **authored** tier and stops there: it writes a great file, attests to its own quality with an LLM self-check (Step 4), and never sees that file again. Keystone has no `/evolve`, no memory, no friction loop, and no way to mechanically verify that the keystone it produced stays true. These proposals move Keystone from authored toward **enforced** — turning its prose "What NOT to do" / Step-4 checklist into mechanical checks, baking the map-not-encyclopedia discipline plus a freshness linter into the output, adding a repo-as-record section to the skeleton, and adding the smallest possible evolution loop that fits a single-shot generator's grain.

The unifying move: **Keystone already knows the rules — it states them as prose the agent is asked to honor. Compile those rules into deterministic checks that hold the line whether or not the agent is paying attention.**

## Proposals (ranked by leverage ÷ effort)

### 1. Output validator: compile Step-4 + "What NOT to do" prose into mechanical checks

- **Maps to finding:** #1 (mechanical enforcers with remediation-as-prompt) + finding #5 row in the comparison ("Step-4 self-check checklist — LLM self-attestation, unenforced"). Harness tier: **authored → enforced.** This is the single highest-leverage borrow in the whole brief, applied to Keystone's exact gap.
- **What changes:** Keystone today self-attests via a Markdown checklist in `plugins/vibe-keystone/skills/keystone/SKILL.md` Step 4 (lines 275-286) — six `- [ ]` items the *agent* ticks by judgment. The "What NOT to do" rules (Step 2 §9, lines 240-251) and the "What you do not do" closeout (lines 331-338) are likewise prose the agent is trusted to honor. Propose a new shipped artifact — `plugins/vibe-keystone/skills/keystone/references/validate-keystone.md` (a checks spec) plus an optional `scripts/validate-keystone.js` (deterministic linter) — that mechanically verifies the *produced* `CLAUDE.md`, not the agent's intentions:
  - **Section presence** — every ALWAYS section heading (Title, Tech Stack, What's where, Common tasks, Conventions, What NOT to do) exists. Maps Step-4 item 1 to a regex over `^##` headings.
  - **Placeholder leak** — no `{actual}`, `{one line}`, `{task}`, `{repo-specific}`, `{path}`, `...` skeleton tokens survived into the output. Maps Step-4 item 3 ("references specific paths... not generic placeholders") to a literal scan.
  - **Path existence** — every backtick-quoted repo-relative path in the produced file (`` `src/` ``, `` `scripts/build.py` ``) actually exists on disk. This is the check no LLM self-attestation can fake. Maps the "References specific paths/files in this repo" intent to `fs.existsSync`.
  - **"What NOT to do" floor** — at least 3 bullets under that heading. Maps Step-4 item 2.
  - **Snapshot-rot scan** — flag enumerated "recent decisions" / "current sprint" / dated bullet lists (the rule at lines 284, 335). Computational where it's a keyword scan; inferential (agent judgment) for the gray cases — keep that split honest.
  - **Remediation-as-prompt:** each failed check emits a fix *instruction*, not a status code — "Section `## What NOT to do` is missing. Add 3+ repo-specific guardrails; see SKILL Step 2 §9." That string goes back into the agent's context. This is the OpenAI mechanic verbatim.
- **Why it pays:** Step 4 is the load-bearing quality gate and it is currently unenforced self-report — the exact failure mode the comparison flags as "big gap, highest-leverage borrow." The path-existence check alone catches the most common keystone defect (hallucinated or stale paths) that no amount of self-attestation will. It makes "done" mean something mechanical. And it's the seed a freshness linter (#2) reuses.
- **Effort:** medium. The checks spec (the `.md`) is one-session. The `scripts/` linter is a second session — but Keystone ships **zero scripts today** (PRIVACY.md asserts no executable surface, no outbound calls), so adding a `scripts/` dir is a real surface-area decision, not a tweak. The spec-only version is shippable without crossing that line.
- **Risk / blast radius:** Spec-only (`.md` checks the agent runs) touches nothing but Keystone's own skill tree — low. The `scripts/validate-keystone.js` version changes Keystone's privacy/runtime story: PRIVACY.md (`PRIVACY.md`) currently states "no scripts, zero outbound, fully determined by SKILL files." Shipping a Node script means updating PRIVACY.md and CHANGELOG, and the validator must stay read-only on source + write-nothing to honor the zero-side-effect promise. No cross-plugin contract touched — Keystone reads `~/.claude/profiles/builder.json` read-only and shares no schema with the Cartographer family, so this is self-contained.
- **Do-now slice:** Write the checks spec as a reference doc the SKILL points to from Step 4 — `references/validate-keystone.md` listing the five mechanical checks + their remediation strings, framed as "run these against the produced file before claiming done." No script, no privacy change, fully reversible (delete one file). It upgrades Step 4 from self-attestation to a named procedure today; the executable linter is the follow-up cycle. **Not written this session** — that would edit the shipped skill tree, which the charter forbids. It's specced here for approval.

### 2. Map-not-encyclopedia output mode + freshness linter

- **Maps to finding:** #2 (AGENTS.md/CLAUDE.md as MAP, not encyclopedia + mechanical freshness). Harness tier: **authored → enforced.** Highest *strategic* value in the brief because it improves every repo Keystone touches.
- **What changes:** Two coupled edits to `plugins/vibe-keystone/skills/keystone/SKILL.md`:
  - **(a) A size/shape discipline in Step 3 (Output discipline, lines 265-273).** Today Step 3 governs formatting (ATX headings, no emoji, em-dashes) but says nothing about *length* or *pointer-vs-inline*. OpenAI's hard-won lesson: the giant instruction file fails — it rots, crowds out real context, can't be mechanically verified. Add a rule: the keystone is a **map** — target ~150 lines; when a section would balloon (architecture deep-dives, long convention lists, design tokens), it points into a `docs/` file instead of inlining. The existing References section (§10) becomes the spine of this, not an afterthought. Note the live example in our own house: the comparison flags the Cartographer root `CLAUDE.md` as "enormous, half auto-generated" — proof the drift is real and Keystone is the upstream fix.
  - **(b) A freshness check** added to the Step-4 self-check and the #1 validator: every `docs/`-tree pointer the keystone emits must resolve to an existing file (dangling-pointer check), and the keystone should carry a one-line "how to tell if I'm stale" pointer (e.g., "if the `What's where` table doesn't match `ls`, regenerate") rather than enumerated state that rots. This is the mechanical-freshness half of the finding, scoped to what a generator can guarantee at write time.
- **Why it pays:** Keystone is the *only* tool positioned to set this discipline at the source — it writes the file every other agent stands on. Fix the pattern once in Keystone and every future keystone is born map-shaped and lint-verifiable, instead of authored fat and left to rot. The comparison ranks this #2 overall precisely because of that fan-out.
- **Effort:** one focused cycle on Keystone (the comparison's own estimate). The map-discipline prose is one-session; the dangling-pointer linter shares the #1 validator's machinery, so it rides that cycle.
- **Risk / blast radius:** Editing Step 3 changes the *shape* of every CLAUDE.md Keystone produces going forward — that's the point, but it's a behavior change to the shipped skill, so it needs a CHANGELOG entry and a version bump (currently `0.1.1` per `plugin.json`). Risk of over-correcting: a ~150-line target could push genuinely load-bearing content into `docs/` files that then go unread. Mitigation — frame it as "map first, but inline anything an agent must see on every task." No cross-plugin contract touched. The README (`README.md`) advertises the current 10-section skeleton; if the shape changes materially, README needs a paired update (flag, don't drift).
- **Do-now slice:** None that ships in the skill — both halves edit the shipped SKILL or add a linter, both charter-forbidden this session. The do-now is *this paragraph*: the proposal is fully specced with line-anchored edit points for Este to approve. The cheapest first real slice (next cycle) is **(a) alone** — the map-discipline prose in Step 3, no linter — which is reversible and delivers most of the strategic value on its own.

### 3. Repo-as-system-of-record section in the skeleton

- **Maps to finding:** #6 (repo-as-system-of-record discipline). Harness tier: **authored** (formalizes a convention) — the comparison calls it "low effort — mostly a convention + a section in the keystone skeleton," and that section is Keystone's literal output, so this is the most direct fit of any finding to this tool.
- **What changes:** Add a new CONDITIONAL section to the Step-2 skeleton in `plugins/vibe-keystone/skills/keystone/SKILL.md` (the skeleton runs §1-§10, lines 85-263). Propose §5.5 or a named "Source of truth" block: a place the keystone *designates* for taste, decisions, and tribal knowledge as versioned markdown — "if it's not in the repo, the agent can't see it." Concretely it tells the produced repo: decisions that aren't MCP-logged go in `docs/decisions/`; design taste goes in `docs/` not Slack; the keystone names *where* out-of-band knowledge must land to be agent-visible. This dovetails with the existing Decisions-log section (§8) — that section handles the *decision* surface; this one handles the broader *tribal-knowledge* surface OpenAI pushes into versioned markdown.
- **Why it pays:** It's the cheapest finding to adopt and it closes a real gap — Keystone today encodes *where decisions log* but never tells the repo to pull taste and tribal knowledge in-repo. This is the principle that makes every *other* harness improvement legible (a linter can only check what's in the repo). Low effort, broad fan-out.
- **Effort:** one-session. It's one new skeleton section + a line in the repo-type quick reference, no machinery.
- **Risk / blast radius:** Lowest of the four. Additive section, CONDITIONAL so it drops when it doesn't fit. Risk: section bloat — adding sections cuts against proposal #2's map-not-encyclopedia discipline. Mitigation — make it a *tight* block (3-4 lines, mostly a pointer), and gate it CONDITIONAL on the repo actually having an out-of-band-knowledge problem (teams, not solo scratch repos). No cross-plugin contract touched. Needs CHANGELOG + version bump when shipped.
- **Do-now slice:** None in the skill (skeleton edit is charter-forbidden this session). The slice is the spec above — a named, ordered section with its CONDITIONAL gate, ready to drop into Step 2. Of the four proposals this is the safest to green-light first because it's purely additive prose.

### 4. The minimal evolution loop — Keystone learns from the keystones it ships

- **Maps to finding:** Evolution-loop gap (comparison axis #6: "Vibe Keystone — Memory/evolution/learning: None"). Harness tier: **authored → instrumented** (a feedback sensor on Keystone's own output). The honest verdict embedded below.
- **What changes — and the honest framing first:** Keystone is a **one-shot generator with no command surface** — no `commands/` dir, no session logger, no friction logger, no `/evolve`, by design (confirmed: the plugin tree is exactly one `SKILL.md` + `plugin.json`; PRIVACY.md asserts zero runtime state beyond reading `builder.json`). Cartographer's 4-level self-evolution stack exists because Cartographer runs *many* commands across *many* sessions and accumulates friction. Keystone runs ~once per repo. **Bolting Cartographer's full stack onto Keystone would be cargo-culting** — the comparison itself warns against copying machinery whose ROI isn't there. So the proposal is deliberately minimal, in three escalating tiers; Este picks how far up to go:
  - **Tier 0 (recommended floor) — capture, don't evolve.** When Keystone overwrites an existing `CLAUDE.md`, it already shows a diff (SKILL line 338). Have it optionally append a one-line friction note to a local `~/.claude/plugins/data/vibe-keystone/regenerations.jsonl` — "repo X, what changed, what the prior keystone got wrong." No reflection loop, no auto-anything. Just a sensor. This is the cheapest possible step from *zero* memory to *some* memory.
  - **Tier 1 — a `/keystone:evolve` that reads the capture.** Mirror Cartographer's `/evolve` exactly in philosophy (read last-N regenerations, propose SKILL edits to `proposed-changes.md`, **never auto-apply**). Only worth it once Tier 0 has fed it real signal — an evolve loop with no capture is the "under-fed capture hole" the comparison already flags in Cartographer. Don't ship Tier 1 before Tier 0 has data.
  - **Tier 2 (probably skip) — drift detection on shipped keystones.** A check that re-reads a repo's keystone vs. its current `ls`/stack and flags rot. This is real value but it's arguably a *different product* (a keystone *linter/doctor*, not the bootstrap generator) — it belongs in a `/keystone:check` command, and at that point Keystone has grown a command surface and stopped being one-shot. Name it, defer it.
- **Why it pays:** Keystone produces the most load-bearing artifact in the whole harness and currently gets **zero feedback** on whether those artifacts hold up. Even Tier 0's one-line capture turns Keystone from fire-and-forget into a tool that can eventually learn which sections rot fastest and which "What NOT to do" rules actually got violated — the raw material every other proposal's enforcement would tune against.
- **Effort:** Tier 0 = one-session (one append-only write, gated behind user opt-in to honor the zero-side-effect promise). Tier 1 = full cycle (new command, new skill, mirrors Cartographer). Tier 2 = full cycle + a product-identity decision.
- **Risk / blast radius:** **This is the proposal that touches the privacy/runtime contract hardest.** PRIVACY.md (`PRIVACY.md`) currently promises Keystone writes *only* `CLAUDE.md` and `~/.claude/plugins/data/`-style state does not exist for this plugin. Tier 0 introduces a new local write surface — PRIVACY.md and CHANGELOG must both update, and it should be opt-in (default off) to not surprise existing users. If Tier 0 reuses the Cartographer family's `~/.claude/plugins/data/<plugin>/` JSONL convention, it touches a *shared directory layout* the Cartographer CLAUDE.md flags as a coordinated surface — coordinate before adopting that path (or namespace cleanly under `vibe-keystone/` and stay self-contained). Atomic-append discipline (the family uses `atomic-append-jsonl.js`) applies if we go there. Tiers 1-2 grow Keystone a command surface — a genuine scope expansion, not a tweak.
- **Do-now slice:** None — needs a cycle. Even Tier 0 crosses the privacy contract and adds a write surface, which is a decision, not a reversible one-liner. The do-now is the *decision itself*: does Keystone stay a pure one-shot generator (close this finding as WONTFIX with rationale), or does it grow a feedback sensor? My read: **Tier 0 is worth it, Tier 1 only after Tier 0 has fed it, Tier 2 is a different product.** Recommend logging that as a dashboard decision before any code.

## What this tool should NOT adopt (and why)

- **The full 4-level self-evolution stack from Cartographer.** Keystone runs once per repo; Cartographer runs dozens of times per project. Friction logs, session loggers, decay curves, and a `/vitals` self-test are calibrated to a high-frequency multi-command tool. Porting them wholesale onto a single-shot generator is exactly the "machinery whose ROI isn't there" the comparison warns against. Take the *principle* (a sensor on output), not the apparatus. See proposal #4's tiering.
- **Throughput-first / minimal-gates philosophy.** Irrelevant to Keystone — it has no merge loop, no PRs, no CI of its own. The comparison flags this as "only responsible at agent throughput"; Keystone isn't a throughput tool at all. Nothing to copy.
- **Per-worktree observability / CDP / instrumented runtime.** Keystone produces a *static document*; there's no running system to observe. The instrumented tier applies to Cartographer's *built apps*, not to Keystone's output. The keystone's "instrumentation" ceiling is the freshness linter (proposal #2) — checking the artifact against the repo. That's the right and only place to stop.
- **A heavy linter that breaks Keystone's zero-dependency, zero-network promise casually.** PRIVACY.md is a real selling point ("no scripts, no outbound, fully determined by SKILL files"). Any executable validator (proposals #1, #2) must preserve read-only-on-source + write-nothing, or it stops being the clean local tool it advertises. Prefer the spec-driven (agent-run) version of every check until an executable linter clearly earns its surface area.
